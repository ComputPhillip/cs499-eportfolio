Purpose and Recording Status

This guide supports a code review screencast for peers or a manager. It covers the original IT 450 checkers program, the weaknesses motivating each enhancement, and the evidence to show in the finished portfolio. The video has not yet been recorded. A suggested length is 8 to 12 minutes; that is a pacing recommendation, not an assignment requirement.

The rubric places the review before implementation. The enhancements already exist, so describe this recording honestly as a retrospective review of the original code and the enhancement plan. Do not claim that a new recording occurred before the changes. Confirm with the instructor how to address the timing requirement.

Prepare the Screen and Files

Open the preserved original/Checkers_v24.py and the three separate milestone folders. Increase editor text size, hide unrelated windows, and enable microphone recording. Keep the original file unchanged. Use the enhanced application for a stable gameplay demonstration and identify that version on screen; do not present enhanced behavior as original functionality.

Prepare a standard board and a small forced-capture position. For the database demonstration, create a disposable named position so the update and delete examples cannot remove a valued save. Open each milestone README, the algorithms benchmark CSV, and the database schema and tests. Rehearse the transitions once before recording.

Opening and Artifact Context

Suggested timing: 0:00 to 0:45. Explain that this portfolio develops one Python checkers artifact across software engineering, algorithms and data structures, and databases. State the computer graphics focus: a readable board, visible legal actions, responsive input, and consistent rendering of game state.

Suggested narration: “My baseline is the supplied Checkers_v24.py from my IT 450 project. It includes a two-dimensional board, standard and custom setups, local human or computer play, and text saving and loading. This specific source uses rule filters and random choice. It does not contain the minimax or knowledge-base implementation described in my earlier proposal.”

Walk Through the Original Functionality

Suggested timing: 0:45 to 2:30. Show Checkers.__init__ at line 11, where the window, tile matrix, state, and controls are created. Follow SetupBoard at line 53 and Play at line 61 to explain the setup and play loops. Show clickInCustom at line 381 and clickInPlay at line 442 to trace how user input affects the board.

Continue to CompTurn at line 73. Show the rule filters and randrange at line 136, explaining that the remaining moves are selected randomly. Show moveIsValid at line 530, move at line 545, and the capture helpers beginning at line 575. Finish with SaveSetupToFile at line 705 and LoadSetupFromFile at line 722. These line numbers refer to the preserved baseline, not enhanced files.

Analyze the Improvement Areas

Suggested timing: 2:30 to 4:15. Explain how Tile at line 764 mixes piece state and drawing. Constructing a tile creates graphical objects, making isolated rule tests difficult. In move, line 555 uses division to form a list index; under Python 3, that produces a float and the isolated capture check raised TypeError. Show the expression and explain the failure without editing the original.

Describe the opponent limitation: filtering single moves cannot evaluate a full sequence of replies. Explain that the text loader clears the board before validating all records and relies on assertions for some values. A failed load can therefore affect the current position. Discuss incomplete test coverage and comments that no longer agree with the implemented random selection. Separate a confirmed defect from a question requiring further testing.

Explain the Three Enhancements

Suggested timing: 4:15 to 7:15. For software design, show the independent model, canvas view, controller, opponent, and storage modules. Explain how immutable piece values and explicit legal moves support tests without opening a window. Demonstrate destination highlights and animation. Note that promotion ends a turn in the enhanced rules, which is a deliberate behavior change requiring documentation.

For algorithms, show the recursive minimax function and the alpha-beta cutoff. Explain that depth counts completed turns, so a forced multi-jump keeps the same player and continues before a leaf is evaluated. Show the deterministic move ordering and one test comparing the search to an exhaustive oracle. In the benchmark CSV, opening depth 4 drops from 1,828 to 459 visited nodes with the same selected move and score. This measures pruning on a fixture; it does not establish tournament strength.

For databases, show the SQLite position-library schema and its relationship between a saved position and its pieces. Demonstrate creating a named position, loading it, updating it, and deleting the disposable example. Explain parameterized SQL, constraints, and transactions using the actual implementation. Show a failure-path test so a reviewer can see why an interrupted update should preserve the prior save. Distinguish saved snapshots from full move replay.

Connect Evidence to Course Outcomes

Suggested timing: 7:15 to 9:00. For collaborative environments, point to clear module boundaries, reproducible tests, and questions for the reviewer; do not claim an actual team review unless one occurred. For professional communication, explain how the video, milestone narratives, and navigable portfolio serve different audiences.

For computing solutions, discuss search depth versus response time and state copying versus compact representations. For techniques and tools, connect Python, Tkinter, automated regression checks, benchmarks, and SQLite to a working application. For security, explain validation before state replacement, parameterized queries, and atomic writes. Acknowledge that these measures are not a complete security audit or an authentication system.

Close and Publish the Recording

Suggested timing: 9:00 to 10:30. Ask for specific feedback on usability, capture rules, test gaps, and persistence behavior. Identify remaining limits, such as no tournament evaluation or full replay. Explain the code in your own words and correct anything you cannot independently verify.
