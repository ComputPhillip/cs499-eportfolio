Professional Focus and Development

My focus within computer science is computer graphics. I am currently pursuing the creation of a game in Unreal Engine, and my next educational goal is a master's degree program specializing in computer graphics. My portfolio presents a Python checkers application as a connected example of interface design, algorithmic reasoning, and persistent data. These experiences support my direction toward interactive software and further study. The Unreal Engine game is an ongoing project, while the strongest evidence in this portfolio is the preserved source, tested enhancements, and explanations of what each result establishes.

Coursework outside this artifact also informs how I evaluate software. In my IT 460 machine learning report, a classifier achieved 95.09% test accuracy but detected only 58 of 90 advertisements. Reporting both results made the limits of the model visible and supported a recommendation for further evaluation rather than immediate release (Gooden, 2026). That example illustrates the same professional value applied in this portfolio: a favorable number needs context, and evidence should support the decision being made. Neither that report nor the checkers benchmark establishes production readiness.

Algorithms and Evaluation

My approach to algorithms emphasizes representation and measurable behavior. The checkers search uses a dictionary board, immutable piece values, explicit moves, and recursion. Depth counts complete turns so that chained captures remain part of the same decision. Alpha-beta pruning is compared with unpruned minimax using the same heuristic and move order. Across nine benchmark position-depth pairs, scores and chosen moves agreed. At opening depth four, pruning reduced visited nodes from 1828 to 459. This is evidence of reduced search work on that fixture, not a universal performance claim.

The trade-off is also visible. Copying boards for child states makes branch isolation easy to inspect, but allocates more objects than an in-place representation. A limited depth makes decisions practical for the interface, but leaves a horizon beyond which the heuristic cannot see. The IT 460 report addresses a related evaluation problem by separating model selection from reserved test evaluation and reporting class-specific errors. Together, these examples support an evidence-based approach to selecting and evaluating computational solutions.

Software Engineering and Databases

The software design enhancement separates game rules, rendering, controller behavior, opponent selection, and storage. This arrangement allows rules to be tested without opening a window and lets the renderer reuse its canvas objects. Animation and search introduce periods when a decision is pending, so the controller coordinates input and invalidates obsolete callbacks. These details show that the quality of a graphical application depends on state management as well as its appearance.

The database milestone adds a local SQLite library of named positions. A saved_games table stores game metadata, and a related pieces table stores the board. Primary and foreign keys, uniqueness rules, and value constraints express integrity requirements. Parameter-bound queries and transactions support creating, reading, replacing, and deleting saves. The interface restores the turn, forced capture, result, opponent mode, and search depth along with the board. The milestone's 31 passing tests include inherited checks plus database and library-interface cases. This demonstrates a structured persistence layer; it does not provide multiplayer accounts, cloud synchronization, encryption, or a replay history.

Security and Responsible Practice

A security mindset begins at boundaries where data or actions enter a system. Checkers save validation checks coordinates, piece attributes, duplicate squares, counts, and capture continuation before replacing the active game. The database enhancement adds integrity controls at the persistence layer. These measures address specific threats to correctness and data integrity. They do not establish protection against every malicious file, operating-system compromise, or unauthorized user.

My IT 460 report extends this perspective to data use. Its proposed policy considers provenance, collection purpose, retention, privacy, and the risk of exposing stored examples. It recommends limiting personal information and reassessing a model when its intended use changes (Gooden, 2026). Those are proposed safeguards, not evidence of an implemented organizational security program. Across both projects, my professional responsibility is to communicate limitations, preserve attribution, and avoid presenting unsupported claims as verified results.
